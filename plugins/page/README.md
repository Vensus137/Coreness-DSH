# The product's page

The product's own surface in the web UI: a row in the left sidebar and the panel that row opens — as wide as the frame's centre column, drawn as two panes: a rail of sections beside the body of the chosen one.

## In the surface

- **The pair.** One keyed cell in the `main` seat and one row in `sidebar.panellist`, both under the id `coreness`: the frame draws the `main` cell of the active panel id, and the sidebar selects that id on a click, so the two registrations meet through the id alone.
- **The rail.** The host's own settings nav, with the product's own first section drawn by the page itself; the rows after it are the sections other plugins register into the seat this page declares (`coreness.section`). A seat nobody fills draws no row, and no code stands for the empty case.
- **The product's overview.** `The product` reads the installed composition and draws the host's own package-page card: the product's name, the version in a neutral capsule tag, the package name the composition installed, and the manifest's one-liner. The composition's rows are deliberately **not** drawn here: what a profile mounts — every row, its phase and its enablement — is the platform's own component list to show, and a count over them with the line naming the rows that did not arrive was this page's second door onto that reading, which left with this round. The read follows the composition while the page stands: the host's `plugin-manager/changed` and a reset connection make it read again.
- **Every state in the host's words.** A read in flight, a deployment without a manageable profile, a profile that does not carry the bundle, and a refused or broken answer are each drawn as the host draws one: a state dot beside the sentence, a reason under a failure, no bare key anywhere. The components themselves are not listed — the roster belongs to the platform's own Plugins page.
- **The picker, a chunk the sections draw from.** A control that offers a settled list is the page's own (`require.async('./client.picker.js')`), never the browser's: the Qoder form's model id and reasoning level, a rate gate row's provider and model, and an MCP server's kind all draw it, and the platform's module loader answers the three pulls with one script and one materialisation, so there is one control and no second copy of it to drift. It names its nodes per instance (`data-picker` and `data-picker-list` carry the instance's own name, because two pickers may stand in one row and a fixed marker would name the first of them to every reader), and **its sheet is the page's own** (`coreness-picker*`), injected by the control itself when it is first drawn (`useStyles` in `client.picker.js`) and claimed by the Loader for this package: the rules belong to the control, not to the sheet of the section that happens to draw it first. An empty value is an option of its own where a caller offers one, and a value the list does not carry is drawn as it stands rather than as an empty box.
- **The status surface, one chunk every card of the four sections draws.** A card's state has one home, one place and one word: `require.async('./client.status.js')` draws it into the right end of the card's own head row, and the place is the component's own rule (`margin-left:auto` in its sheet), so no section carries a place rule and a status cannot stand anywhere else. The words are one map, `STATUS_WORDS`, the only place a sentence or a tone is written: the entry a value names gives the sentence its subject **and** its tone, so a green mark beside a refusal is not a shape that file can express, and a card with nothing to state draws none of it — an element with a place and no words would be a reserved box, and the page keeps no reserved boxes. **The corner keeps the word alone, and the dot stands beside the name of the thing it is about.** The second drawing of this surface is the dot a chunk draws beside a name (`statusMark`), and a card that read nothing draws no dot rather than claiming a connection nobody asked about. A state a reader is simply *in* keeps no word: `Token is set` and `Token is not set` left the face on the user's word, and the dot says them instead — out loud, through the mark's own accessible name, where no word stands beside it. Where the word stands is the surface's own rule and where the dot stands is the drawing chunk's; the look of both is the status surface's own sheet. Nothing that is not a state reaches the face: no request id, no URL, no path, no vendor's own body, no `Settings → Models` instruction, and never the credential reference. What must stay visible without standing on the face splits three ways: **the state on the face, the act in the log** (`statusDetail`, the one door to the console, called where the answer arrives rather than where the status is drawn) **and the content in the card's body.**
- **A section's chunk, and what a chunk that never arrives costs.** The product's heavier surfaces are package-local chunks (`client.<name>.js` beside the entry), pulled by the entry the way the platform's own packages pull theirs; each registers its own section into `coreness.section` and reads its plugin's own route alone. A chunk that never arrives leaves its row out of the rail and is named on the console, because nothing on the page could say it. **The two kinds** a row may name — the platform's own transports (`streamable-http`, `stdio`, read by `plugins/mcp/row.js`) — decide which fields the form draws and sends: the chosen kind's alone, so an http row carries an address and its headers and no command, and a stdio row carries the command, its arguments, the environment and the working directory, while the call timeout and the loud-startup sentence stand on both. A row whose fields belong to neither branch is refused in words rather than written, and a row of a kind this page no longer offers reads, shows and connects as the `stdio` row it is.
- **The sign-in a row asks for: where it is offered, and what a person does with it.** A row that wants OAuth carries a control **only where the press can change something**, and that is settled before anything is drawn: the page's own route asks the flow's discovery at the row's own address — the pointer the `401` named first, the standard's well-known address after it — a row **whose tools stand is left alone** whatever that probe met, and a row no flow answered for is offered nothing in its strip, so there is no button that could only refuse and no window of ours anywhere in the path. For a server whose door the standard's signals do not announce, the same press stands in the **row's own settings** — the same door, the same act, one place at a time — which is the only way such a server can be signed in at all. The attempt itself is the platform's: one attempt per key, started by the page's host half through the authorization registry, with the interaction travelling **with the request** (`{notify, prompt}`), because the platform registers no client-facing door to that registry — so this page carries it: the flow's own address stands as a link in the card's body, the flow's own question is drawn where the person is looking **in the page's own field**, and the person's answer travels back through the same route. **The flow's own state is said in the card's body and never in the strip**: the strip is the room of the row's own condition, and a word of the flow's standing there is read as the row's (`waiting` beside a row that is merely connecting) while the same sentence is said twice on one card — so the strip keeps the row's condition alone. The body carries **one sentence whose own words carry the address**: the flow's sentence is drawn as it came, with `sign in` inside it as a link — the anchor's own class `coreness-mcp-signinLink`, underlined and taking the colour of the words around it, because the page's own vocabulary carries no link role: the two anchors this page drew before were the credits' own icon (a glyph named by its `aria-label`) and this block's bordered `Open the sign-in page`, which wore a control's classes — and no bordered control stands beside the sentence; under that sentence the field's own line holds the page's box with `Send` at its right (`coreness-mcp-signinLine`), the flow's own question stands **under** that line as the hint (`coreness-mcp-signinField`), where a person reads it as the hint to the box he is typing in, and **the reset (`coreness-mcp-signinWithdraw`) stands only while the attempt waits for its code**, as the block's own last line at its **left** edge — the owner's own placement, and the edge every other line of the block begins at — a person takes back what is pending and nothing else, so a withdrawal and a refusal carry none, and the way on from a refusal is the head's own `Sign in` control, which starts a fresh attempt — the link stands only while an attempt waits, because the address of an attempt the flow no longer holds is not a way on; the field's box and the controls on that line draw 36 px in the browser where the declared values — 6 px of padding, a 22 px line, a .5 px border and the page's own `box-sizing` — add up to 35, so here the measured box is the fact and the equality of the field and the control is what the line needs. The body carries a refusal as **one short sentence and the code itself**; the flow's own long sentence — with the address, the endpoint and the parameter it names — goes to the console, this page's door for a reason that may not stand on a face, so every branch reaches a reader and none ends in silence. A grant the attempt committed is joined to its row by the row's own reference header and by the row being loaded again — the transport holds the headers it was built with — and never over a header a person wrote. **A removal drops that server's records first**, through the flow's own call, so a row added again is signed in again rather than silently remembering a token; a drop that refuses does not hold the person's press and is told in the console. The attempt lives in the page's plugin and nowhere else: a restart loses it, and a lost attempt reads as **cancelled**, offered again, and never as pending for ever.
- **The reason a row did not start: one sentence, first in the card's body.** The platform keeps the reason — the error the row's plugin died of stands on the fiber the Loader holds, with the error the SDK raised under it as its `cause` — and publishes it nowhere: the inventory and the plugin manager carry the phase alone, and the picture carries the client's newest line, which for a row whose activation ended is the retry it will never make. So the page's own door reads the record where it stands (`fiber.await()` rethrows it) for the rows the picture reported `failed`, and the sentence drawn is the **server's own message** whenever its answer carried one — out of the responder's body as the platform kept it, or out of the SDK's own sentence where that path appends the body to it — and this page's own sentence per family otherwise: a `403` understood and refused anyway (a region, a plan, a policy), a `401`, a `404`, a `5xx`, an address that answered but not as an MCP server, a connection that closed, a door that never answered, and a record whose shape names no reason this page can read. It stands **once**, above everything else the body carries, because the tools line under it reads as its consequence; the strip keeps the row's one word; and the platform's own record — the status, the SDK's classification, the body as it came — goes to the console, the third room of the split this section's status surface names. The reading is asked about the failing rows when that set changes and not on every read, and the record is said to the console once per new record. **It stands on the installed assembly's own shapes** — `cause`, `status`, `data.text` — because no door publishes a failed row's record: a platform that moved them leaves the family standing and the server's words missing, and the sentence drawn is this page's own then, which is why the family is decided before the words.
- **The credits widget, a chunk in the sidebar's own foot.** `require.async('./client.credits.js')` registers into `sidebar.footer.action` and draws the account of the route: the spend as a ring, one summary, and a popover with the vendor's usage link, a block per account, the rewards with a mark each, and the reason when a reading failed. Its figures are the product's own route (`/api/coreness.credits`), never this row's settings section — that section is the profile's Cordis patch, and the donor rewrote it on every sweep.
- **The Qoder section, two cards in the look of the platform's own settings sheet.** **Connection**: the route's standing — declared and registered as a provider, declared without the settings namespace it names, registered alone, or absent from this profile; the reference the declaration carries; whether a value is stored behind it; the field that writes one, and the clear beside it; the vendor's own verdict on the value the store holds, and the press that asks for it again — three answers, told apart by tone: the vendor takes it, the vendor refuses it in its own words (this section's red), or the question could not be put (dim: an unreachable vendor, a queue, an exhausted allowance, a profile holding nothing — never a broken token, which is the defect the check exists for, read from the other side); and, in the same card, the node's row: the address the requests go to, and one press that asks the node map, pins the node that answered and reads the row back.
  **Models**: the row's own list, edited as the donor edited it — a row per model whose id is chosen from the vendor's live catalog in the page's own picker, with its window and its input pair (`Text` is the vendor's own claim and is not ours to clear; `Image` is the row's), and a removal — under them `Add row`, `Reset to defaults`, `Cancel` and `Apply`, with the first refusal of the draft drawn in place of a summary and `Apply` standing off while it stands. **The write is one door:** the value is handed to the platform's credential store and read back before the page calls it stored, an empty field writes nothing, and the model list and the node are written with `settings.mutate()` at the revision this section read — so a write that raced somebody else's is refused as `settings/conflict` and drawn in words instead of overwriting it, and **every write is followed by a re-read: the fields show the section, never what was typed before it.** Two refusals are named rather than left as empty places: the row's fallback window has no field of its own (a model id the row does not declare takes it, and `Reset to defaults` returns it to the patch), and the route's own effort is not written by a control of its own — a row names one, an untouched row names nothing and the route's answer stands, which is what the field's own `title` shows.
- **The levels a row offers are the levels its own model publishes.** The control is the page's own picker, and its options are that model's menu as the vendor's live catalog answers it, plus the level that stands for the row when the menu does not name it (the row's own, or the route's own effort where the row names none — so the control always draws a value it can also offer) and one level of ours — `Off`, marked as ours, because no vendor menu publishes it and without it reasoning could not be switched off at all. A menu nobody could read, a model the listing does not carry, a model that publishes no menu, and a level the menu does not name each say so under their own control, and the row keeps standing in all of them. The vendor's live catalog is its own round trip: the cards stand on the platform's own doors at once, and the id picker waits locked with `Reading the live catalog…` beside it until the node answers — a section that waited for the vendor would hold the credential and the node behind a node that may be slow, or behind a credential that does not exist yet.
- **A state does not move the layout.** Whatever the section has to say — a value stored, a list applied, a refusal, a revision that moved under the draft, the catalog still on the wire — stands in the card's own header, to the right of its title, in the room the header gives it beside the title; the words a state replaces never sat in the flow of the card, so a state cannot push a control down or move the cards below it. Nothing here is reserved: the header takes the height of its tallest line, and a state longer than that — the platform's own catalog refusals run to two hundred characters or more — wraps inside the slot and grows the header by the lines it needs: that is the named boundary of the rule, measured, and it is why the sentence is never cut. Two things legitimately stand outside a header and are named rather than hidden: a sweep that raised no node lists its per-node reasons under the node card, and a card's own height grows with the rows the reader adds to it.
- **The rate gate's section: the limit, one card per model, and two doors.** `require.async('./client.gate.js')` registers the third section into `coreness.section`, under the row id `gate` and after the two beside it, and draws the limit the plugin holds at the platform's provider adapter. **The limit** — the four numbers a profile may write (`windowMs`, `maxWaitMs`, `thresholdRatio`, `dryRun`), the card showing the first three with a word each on what they do, all read at the revision this section read. Each carries no mark of where the number comes from and none with a press that returns it to the schema's default — the user's own word took both off the page, and the schema's default is untouched by that: a field the page does not show is written as the file has it. The section's card carries `Apply` alone, a row carries `Remove` and `Apply`, and `Cancel` left both by the user's own word («Cancel убираем»): this card carries no `Reset to defaults`, so **a draft of this section can only be applied** — the way back is a fresh read of the file, the section reloaded, while a number typed and not yet applied still stands in its field to be fixed. **One card per model under a ceiling**: its head is the disclosure — the pair, a tag with its ceiling, the window as it stands (used, reserved, how many wait and for how long), and the two marks a user must not miss (a pair this profile's registry does not advertise, and a row the gate would not use with its reason) — and its body carries the pair chosen in the page's own picker from what the route advertises, the row's own two optional numbers, the counters, the estimate factor, and the ring of the last decisions.
  Under the cards stand the rows the gate refused, each with the gate's own reason, and the per-provider sum, which is what the key faces and not a limit this section enforces.
  **Two doors, and they are not interchangeable**: the picture comes from the plugin's own route (`GET /api/coreness.rateGate`, read-only, never written by the page) and every write goes through the platform's settings service at the revision this section read, so a write that raced a hand's edit of the profile's patch is refused as `settings/conflict` and drawn in words — the draft dropped and the row read again — instead of overwriting a value nobody saw; another refusal keeps the draft and shows the platform's reason, because it is about this write and not about the row. Nothing is written on a keystroke: a number typed digit by digit is a draft, and `Apply` writes only what changed — one `set` per scalar, and for the models one `set` of the whole `limits` array, since a volatile field inside a row is refused by the schema itself. Every sentence the section says about itself stands in **one room of its own** under the caption — the height of what it says, with nothing reserved (the user's own word took the two reserved lines off the page) — so a loading, a refusal or a conflict never stands among the fields, and the cards below move only by the lines the sentence itself takes.
- **Two genres of an answer, and how a reader tells them apart without being told.** A **state** is what stands without a press — a card's own word (`Connected: … · 15 models`, `enabled`, `readonly`) and the verdict about the value it judged — and it stands in the state's room in the card's header, drawn in the host's state genre. **News** is the answer to a press, and it stands in the strip on the right of the header of the card the press was made in, then fades — **and only there**: a press made in a row answers in that row's card, a press made in a section's own card answers in the section's, and where the pressed card is gone by the time the answer exists the word stands **nowhere** rather than in a neighbour. The case is a fresh row taken off the draft by its own `Remove`: the press removes the row, the card goes with it, and the leaving is the whole answer — the section's card is the system defaults and says nothing about what was done to a row. **One state is drawn in that same strip, by the contract's own word**: a row the host reports about carries the one-word condition of that row there whenever no press has just answered — the strip is a room already reserved, so a word that comes and goes moves nothing — while the host's own sentence about the row stands in the console and never on the face.

## Dependencies

- **The web shell's seats.** The row registers into the `sidebar.panellist` list and the panel into the keyed `main` seat, both declared by the platform's own packages (`@deepseek-ai/dsh-client-ui-sidebar`, `@deepseek-ai/dsh-client-ui-layout`). The registrations go through `ctx.slots.inject`, which waits for a declaration, so the load order does not matter and a missing neighbour leaves the plugin mounted with no surface rather than failing.
- **A section is handed no id of its own row, and that is the platform's contract rather than a gap of ours.** The props a registered component receives are composed from the five framework shares, and an id of registration is not among them. What the shell keys a contribution by is the **address of the call** that renders it: the platform's own renderer elects an entry by `opts?.entryKey` for a keyed slot and guards every entry by `entryKeyOf(entry)`. A section therefore knows the seat it was registered into and not the id of the row that registered it, so a namespace that **is** that id (the rate gate's `value.ns` is one) cannot be known without asking: it arrives with the route's own picture. The first round-trip is a property of this contract, not a defect to be fixed by reading harder.
- **The platform's remotes as the door to the profile's facts, read-only.** The overview reads `pluginManager.listBundles()` behind the `pluginInventory.list()` gate the platform's own Plugins page applies first, and takes the four fields its card draws from the bundle entry itself — the name, the version, the one-liner and the enablement — so the browser half repeats none of them. The read is invalidated as the host invalidates that page: `ctx.remote.$on('plugin-manager/changed')` and a reset connection make it read again while the page stands. **Nothing of the composition's rows is read here, and no route of this package answers them**: the rows a profile mounts are the platform's own component list, which reads the same Loader's tree and names every row with its phase — the page's own count and difference line were a second door onto the very reading that list publishes, and left with this round.
- **The platform's own doors to a route's facts, asked rather than known.** The Qoder section carries no list of its own: the route's declaration reaches it through `llm.listConfigurableProviders()`, the settings namespace that declaration names through `settings.describe()`, the presence of a value through `credentials.describe([ref])`, the two writes through `credentials.set()` and `settings.mutate()`, and the model the agent uses with its description and the effort in force through `session.modelCatalog()`. **The vendor's live catalog comes through the route's own door** — `POST /api/coreness.qoder {action:'catalogue'}` — and not through the platform's discovery door the section does not ask: `llm.discoverModels` projects each entry onto five fields twice over, so the per-model reasoning menu died between the route and the page, and one read gives the ids and the menus together, so two roads cannot drift apart. The discovery door stays registered for the platform's own model picker, which is the surface that offers a model to adopt. The reference travels one path and only that path — the declaration's settings path down to `apiKeyEnv`, the route the platform's own Models page walks — because a composition read cannot stand in for it: the manager's entries carry no row config, so a key name derived here would be a key the route never reads. The catalog is asked once per mount and kept across every re-read of the settings, because it is the node's own answer and no write of ours changes it.
- **The vendor's verdict on the value the store holds comes through that same door**: `POST /api/coreness.qoder {action:'verify'}` puts the value behind the row's reference to the exchange every turn enters by — one call — and answers with a closed vocabulary of three (`accepted`, `refused`, `unsettled`) carried as a result rather than as the route's refusal, because "the vendor does not take this value" is an answer to the question that was asked. The store can only say that a value is *there*, and a token that expired or was revoked reads as configured until a turn failed, which is what sent the owner to replace a token that was never at fault. The check is asked when a value is handed over and when the reader presses again, never on a tick: one exchange per write, one per press, none on an open.
- **The gate's own route, read as a picture and never written.** The rate gate's section asks the plugin's `GET /api/coreness.rateGate` for the live window and asks nothing else of the host half: the namespace it writes is the one the picture names (`value.ns`), not a constant of the page, because the namespace is the row's id and a second copy here would drift from the assembly that mounts the row. The write is the platform's own settings door — `settings.describe()` for the row and its revision, `settings.mutate(ns, ops, revision)` to write — the same door the platform's own Models page uses, and the route never carries one: a page that wrote through the plugin's route would be writing around the platform's conflict check. The picture is read again while the section stands, because the window moves with no session event: one read on the mount, one after every write, and a beat of two seconds that a hidden document skips — a glance at another tab is not a reason to ask the host for a picture nobody sees.
- **The page's own route carries one face: the sign-in door.** `POST /api/coreness.page` takes the acts a sign-in needs (`sign-ins`, `sign-in`, `answer`, `cancel`, and the `forget` a removal asks for) and answers each row's state as the flow itself answered it. The flow's codes travel as they are — the page draws its own sentence for each of them — and the door's own refusals are spelled apart from the servers route's vocabulary, because one code carried by two vocabularies leaves one branch drawing the other's sentence. Nothing of ours is drawn as a window in that path: the flow's own address is a link a person opens in their own browser, and the callback comes back to the flow's own route.
- **`react`**, taken from the shell's frozen module table; the platform's own control library is deliberately not among them, and the marks it would have given — the state dot, the capsule tag — are the host's own CSS carried by its tokens. The services the browser half injects stand in its own `inject` list.

- **One dictionary per locale.** The visible text is registered under the namespace `coreness` in `en` alone — the chunks carry their own, `coreness.mcp`, `coreness.qoder`, `coreness.credits` and `coreness.gate`; the chain of any other language ends at `en`, so one dictionary answers for every language. The tag words are the host's own.
- The plugin is a row of the composition; without the web composition (the web application in the profile) the host half mounts and no surface appears.

Every platform fact above is read in the installed assembly rather than remembered: `node scripts/harness.mjs` (`probe`, `grep`, `cat`) is the reader that shows each of them, so a reader of this file does not have to trust them.

One row per kind of change this page takes: where it lands, and what says it is whole. The whole set is the plugin's own batch, `node --test "plugins/page/test/*.test.mjs"`; a row adds a live step to it only where the batch cannot see the thing being changed. The place is named by its own name and never by a line, because lines rot.

**A value that looks absent is often a value read at the wrong level, not an absent fact: fix where it is read, not the reading.** The Rate section's own case is the one to remember — `draw(view, act)` is handed the section's *state*, and the picture a press reads as `state.view` stands one level in, at `view.view`; a guard over the reading would not have helped: the level is the fact to read rightly, and the fix was one line and no guard at all. **One browser half, several sections: how a chunk stands beside the entry.** The entry `plugins/page/client.js` asks for each section with `require.async('./client.<name>.js')` (over its `CHUNKS`; the platform's own package does the same), and each file beside it registers itself as a chunk of the same package: `window.__ModuleLoader__.load({ id: '@coreness/dsh/client.gate.js', factory(require) { … } })`, and the same head in every chunk beside it. **The name is the whole rule:** the node half accepts a package-local chunk only when the file name matches `CLIENT_CHUNK = /^client\.[A-Za-z0-9][A-Za-z0-9._-]*\.js$/`, and the request URL must equal `chunkUrl(id, fileName, rev)` for the row's current revision — any URL that does not equal it is answered **404**, while the platform's combo form answers 200. **The file is read from the entry bundle's own directory**, so a hand-written `client.<name>.js` beside `client.js` is served as it stands and needs no build of its own — a requirement of placement, not of build provenance. **The revision in a chunk's URL is the entry bundle's build identity, not the chunk's own bytes** — `artifactRevision` hashes `mtimeMs`, `ctimeMs` and `size` — so an edited chunk is re-read on the next **launch** and not by a reload of an unchanged URL. ## Boundaries

- **No route of its own for the panel.** The panel is selected through the layout service, the selection lives in memory and does not survive a reload; the platform's web surface has no routes. The package's one route is not a page address: it serves the composition's own read to the browser half that asks for it by name, read-only, and neither the panel nor the selection travels over it.
- **Read and display only.** Enabling and disabling a plugin stays on the platform's own Plugins page: the manager's write remotes exist, but a second set of switches here would be a second owner of one profile file — and switching the product's own row off disposes the page that holds the control.
- **One value, one door.** A credential is written where the platform keeps credentials, under the reference the route's own declaration names, and it is the store's answer that says whether a value is there. The section keeps no copy of the token, no second reference and no second notion of "configured"; the models it draws are the route's catalogue, not a list of its own. Whether the vendor **takes** the value is a second fact, and it comes from the vendor alone, through the route's own action: the page asks and never judges, and an answer that is not the vendor's own statement about this value is drawn as a question that could not be put — never as a refused token.
- **A setting is written through the platform's door.** The node, the model list and the fallback window go through `settings.mutate()` with the namespace the route's declaration names and the revision `settings.describe()` gave; nothing here writes the profile's patch file, derives a path of its own, or reads the value back from anywhere but that door. A revision that moved under the draft is the platform's own `settings/conflict`, drawn in words, and the fields then show the section as it stands.
- **A default is not a claim.** The row's `vision` is written on every model the editor applies, `true` included, because this route's schema defaults it to `true` while the donor's left it optional: an omitted key would come back as a claim the box could never clear. The other direction is refused rather than filled — a window or a display name the user empties is left out of the write so the schema's own default stands, and the reason is named in the card.
- **A seat is taken as it is, never styled around.** The sidebar's foot lays its occupants in a flex **row**, and the donor forced it into a column with a rule aimed at those generated names. The platform's instruction to a plugin author keeps the tokens as the only shared styling dependency and tells a copy to rename what it takes under the plugin's own prefix; its own sentence about another plugin's material is narrower — do not read another plugin's DOM, stylesheet or component source *to estimate placement*, and choose a slot that already allocates space — so the credits widget registers into the seat as it stands and takes `wide`/`narrow` from what the seat hands over.
- **No platform library.** The controls are the product's own, written in the host's tokens; the platform's instruction to a plugin author forbids loading its client packages, and its own look is matched rather than imported. The one control three sections share lives in `client.picker.js` and is reached through the platform's module loader's own pull; its sheet is the page's (`coreness-picker*`), claimed by the Loader for this package — never a rule inside a section's own sheet, and never a native select, whose popup is a second design language inside one settings sheet.
- **No second shell.** The frame, the sidebar and the right column belong to the platform; the page takes the `main` seat and leaves every other seat as it found it.
- **No second roster.** The components of the profile are the platform's own component list, and this page draws none of them: no head, no count, no line of names. The one list it draws is the MCP section's own — the rows of the profile's servers file — and a row of the composition is named nowhere here, whatever its state.
- **No kit.** The rules travel with the repository and the procedures are files in the environment's user root; the package carries neither and writes into no environment file.
- **The seat is offered, not filled.** The page declares `coreness.section` and its rail draws every section registered into it; the page's own overview is the section the rail opens on, and the sections of later plugins arrive as chunks of this package or as plugins of their own.
- **One browser half per package, so the plugin is the package root.** The web shell loads client halves by packages and composes one row per package, which is why the patch row names `@coreness/dsh` and the browser factory carries the same id. A plugin addressed by a subpath cannot have a browser half: the row is mounted by the host and the browser never hears of it.
