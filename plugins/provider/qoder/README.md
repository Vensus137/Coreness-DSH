# The Qoder route

Two parts in one plugin: **the wire** and **the route over it**.

The wire is our own way of speaking to the Qoder contour, read off the contour itself and from nothing else: getting in (the node map, the token exchange, the refresh, the profile), the COSY signature, the body and its encoder, and the reading of the answer's frames into channels. It stops at the frames — it declares no models and registers no adapter of its own.

The route is `adapter.js` plus the mount in `index.js`: one adapter under the id the live profile already names (`qoder`), which maps those frames into the platform's own chunk vocabulary, classifies the ends of an attempt, and declares to the platform the models, the retry policy and the credential door. Everything the platform's doors show of this route comes from that declaration.

The package is host-only: its row names a subpath, and a subpath row carries no browser half.

## Dependencies

- **Node's own `fetch`, `crypto`, `fs`** — no vendor SDK and no borrowed client. The signature is `crypto` RSA and AES over the contour's own constants (`sign.js`), the encoder a byte substitution over base64 (`body.js`), the frames read as text (`frames.js`).
- **`@deepseek-ai/schemastery`** for the row's config, as the journal plugin does.
- **`@deepseek-ai/dsh-timeout`** (manifest, `0.2.0-rc.2`) for the three ceilings: `clampTimeout`, `deadline`, `idleWatchdog`, `timeoutOf`. **Their machinery rather than our arithmetic**, because the rule we need is exactly the rule that package states: the watchdog arms only while a read is outstanding and rearms on any byte, so a consumer's thinking time is not counted as the vendor being idle — by construction, not by our remembering.
- **`credentials`** — the platform's credential seam, injected as a service. The token is asked for **on every call** rather than cached, so a rotated token applies to the next request without a restart; a reference that is not set is not an error of the store but the route saying, in words, that it has no credential yet.
- **Where the token is entered.** Once, and never into this package: *Settings → Models*, or `$DSH_HOME/.credentials.yaml` under `refs:`, or the launching shell's environment, which wins over both. The row names the reference (`apiKeyEnv`, default `QODER_PERSONAL_ACCESS_TOKEN`); the value never appears in a config, a patch, a log, an error message or a report.
- **The machine id** is read from the vendor CLI's own file when it is there (`~/.qoder/.auth/machine_id`), otherwise generated once and kept under the harness home (`$DSH_HOME/qoder/qoder-machine-id`, owner-only). One machine, one id, whichever door is used first.
- **The account's credits, over a route of this product's own** (`CREDITS_ROUTE`, `/api/coreness.credits`): the figures are an **observation**, not configuration, and they never enter this row's settings section (§The account's credits).
- **Nothing else.** No settings surface of its own, no price: decisions of the spec, not gaps of this plugin.

## In the surface

- **The row.** The id `coreness-qoder` and the module `@coreness/dsh/plugins/provider/qoder`; its settings are the schema's own — the credential's reference, the model list with the fallback window, the retry policy, the three ceilings, the two addresses with the inference node, and the credits' cadence (§The ceilings, §The account's credits) — and the shipped profile's row sets four of them: the reference, the first-byte ceiling, the retry policy and the credits. The addresses and the inference node have defaults of the contour's own and exist only to be overridden in a test.
- **What it opens.** One service, `qoderTransport` (`endpointMap`, `resolvedEndpoints`, `exchange`, `profile`, `identity`, `machineId`, `catalogue`, `chat`, `frames`, `renew`, `origins`, `ceilings`, `strikes`): `chat` hands back what went on the wire and the answer as a whole, `frames` reads that answer under the ceilings, and the caller decides what the frames mean.
- **One door for the widget**: `CREDITS_ROUTE` on the connection, and the sweep behind it (§The account's credits).
- **One door for a surface that offers a model to adopt**: the vendor's live catalog, registered behind the platform's discovery door under this row's settings namespace (`registerModelDiscovery`). That projection is **five fields** (in the service and again in the remote schema the client half validates with), so the per-model **reasoning menu** does not survive it.
- **The route's own door is what the product's page reads**: `POST /api/coreness.qoder` answers `probe` (the node sweep the page presses), `catalogue` (`transport.catalogue` verbatim: ids, menus **and the vendor's price multiplier** in one answer) and `verify` (one `transport.exchange` with the stored value, in a closed vocabulary of three: `accepted`, `refused`, `unsettled`) — a refusal names all three. The multiplier travels as the vendor sent it (`priceFactor`, `originalPriceFactor` beside it where published, `0` on more than one model) and never as a word: one live entry contradicts its own `is_free`. **It does not reach the platform's own model picker** — the discovery door builds `{id, name, inputModalities, contextWindow?, maxTokens?}` by hand — so the discovery door stays for the picker that offers a model to *adopt*, while the chat's selector cannot show a price.
- **The address of a turn.** The node map is asked anonymously at the centre; the job token and the profile at the OpenAPI host; the catalogue and the chat turn at **the first inference node the centre's map names**, with the whole path in the URL (the node is a **host**, and `/algo` is part of the path). The route reads the centre's map, the narrower one: the centre names **one** inference node, while a node's own map answers the same path with **three** — `api3, api2, api1` — all serving the identical catalogue of fifteen models. Nothing on the write path can choose between nodes, so the route takes the first the centre names and says which source that is, rather than implying an account was granted one node.

## The route, and what it declares

The adapter is a **plain object**, not a subclass and not an import of the platform's base class: the registry duck-types it, and a thrown error keeps its code only when it is an instance of the harness's own error class (`harnessErrorCode`). So **our failure codes travel in a terminal `finish` chunk we yield ourselves**, and the adapter never throws out of `stream`.

- **The mapping** is the whole of the platform's vocabulary: `block-start`/`block-end`, `text-delta`, `reasoning-delta`, `tool-call-delta`, `usage`, and exactly one `finish`.
- **The vendor writes `usage` after its `finish_reason`**, before `[DONE]` (three frames in that order, measured live), so the terminal is **held until the usage arrives** — a turn's price is part of its answer. Whoever maps these frames must emit the usage **before** the terminal chunk, never after.
- **The argument string travels untouched, unparseable ones included.** The harness degrades an invalid JSON argument to text and the tool's own validation yields a tool error result the model can answer, so a malformed call does not end a session; an empty one becomes `{}`. `MALFORMED_RESPONSE` is kept for the shapes **we** cannot read: an id or name that changes mid-call, an unreadable frame, an unmapped finish reason.
- **The classification of an end.** Reasoning without text is `EMPTY_RESPONSE`; a dropped summary of 2000 characters or more is `CONTEXT_WINDOW_EXCEEDED`; a stream that stops without its sentinel and without a terminal frame is `TRANSPORT` — not `STREAM_CLOSED`, because the remedy is the same as for every other transport failure and the retry policy is where it lives; a chunk carrying the far side's own `error` ends the attempt as `SERVER`, in the contour's own words with its status beside them.
- **A saturated queue is a rate limit, not an authentication failure**, even under an authentication status: `codeFor` classifies a body naming `isQueued`/`queueCount`/`serviceAvailable`/`retryAfterSeconds` as `RATE_LIMIT`, because an authentication code is outside the platform's retry set and a fresh token does not bypass a queue.
- **The retry policy** is the platform's own shape and defaults with one addition: `MALFORMED_RESPONSE` joins the five retryable codes (`EMPTY_RESPONSE`, `RATE_LIMIT`, `SERVER`, `TIMEOUT`, `TRANSPORT`), because one tool call whose arguments do not parse has ended whole agent sessions in this project while such an attempt carries nothing durable to repeat and a re-ask is a fresh sample. The list is declared **in the row**, so it can be narrowed without a code change; the registry captures the answer once, so the adapter hands back the **flat, resolved** policy the listener reads.
- **The harness prompt reaches the model through the message, not the field.** The platform hands a route the prompt as the **leading `system` message** and asserts no separate field exists (a loop-built request carries `options.system === undefined`, and both platform providers read the prompt out of the messages). `body.js` flattens **every** system-role message into one string in their order, with a caller's own `options.system` as the prefix, and **sends that string twice**: as the envelope's top-level `system` field and as the **leading `system` message** of the wire's own list, which is the one the vendor's gateway reads. The field alone is accepted and **not read**: a prompt carried in it moves the vendor's count and cache by nothing, and a passphrase standing in it is answered "none was provided in my context", while with the message the same words are read and the passphrase comes back named. This route declares `systemPromptUpdate: 'in-history'`, so the harness **appends** a changed prompt as a new system message rather than rewriting the leading one, and flattening them all is what keeps the earlier text from being lost.
- **The declaration** is four registrations, each in the platform's own place: the transport as a service, the adapter under the route id, the route in the configurable-provider directory, and the vendor's live catalog behind the **discovery door** (`registerModelDiscovery`). The *list* of models the platform routes by is the row's, not the vendor's — a picker that waited for a token exchange and a node map would show up empty. `listModels` is the row's declaration (what the harness may route to) and the door is what the node advertises (`discoveredModels`, leaving out a window or ceiling the node does not publish rather than filling it with this row's fallback).
- **The effort is declared the same way as the models, and for a harder reason.** Each model's declaration carries the platform's three words plus the level the row names for it (`declaredEfforts`), and `defaultEffort` is that level — the row's own value, or the route's `reasoningEffort` where the row names none. The platform validates every effort against that list before any provider I/O and materialises `defaultEffort` into the config the adapter is handed, and that value reaches the wire: a row naming `xhigh` declares `xhigh`, and a declaration naming nothing would have every turn on an untouched row arrive at a platform word instead of the vendor's own. The vendor's live menu stays deliberately **out** of that list, because it would make the catalogue build wait on the vendor and a session's vocabulary would move under a level already chosen.
- **The reasoning flag is a claim about the model, and the route sends the catalogue's own read of it.** Where the catalogue has answered, `model_config.is_reasoning` and `chat_context.extra.modelConfig.is_reasoning` carry the catalogue's flag; the vendor's own builder reads a record it does not have as `false`, but its client cannot reach that branch — the model it sends comes from the catalogue — while this route's list is the row's own, so the branch is reachable here, and on doubt the rule is to err toward more reasoning. A request that asks for `off` overrides the record: a request that turned thinking off must not claim to reason.
- **This route substitutes nothing**: the user's decision is that the control and the row carry what the model's own menu names, and the wire takes a name a menu does not publish — a turn has carried `max` to a model whose menu is `xhigh|low|medium` and been answered normally with `finish_reason: stop`, and `xhigh` has reached `auto`, which publishes no menu at all. The menu is the client's own guard and **not** an enforced ceiling; what the shipped rows name, and why the two menu-less models name the highest on the scale, stands in `plugins/provider/qoder/index.js`.
- **Where the catalogue has not answered, nothing changes**: the flag is derived as it was before this joint and the effort the user named — `max` included — travels as it always did, because the catalogue is a control call under the 10 s ceiling and may be down while the row's model list is deliberately independent of it. A declared Max is never dropped by a control call that did not answer. The list is read **once per transport**, on the first turn that needs it, and a failure is remembered and reported once through the transport's `warn` channel — the one the token renewal uses — so a node that is down does not become a control call on every turn.
- **The identifiers one request carries.** `chat_record_id` and `request_set_id` are one digest of the **request's own head** (the wire model, the flattened system prompt, every message and the tool calls); the **output budget is not in it**, because the platform's retry re-asks the same step and may reach it with the budget re-derived, and a value that moved with the budget would make the re-ask a *different request*. `request_id` is fresh on every request.
- **Pictures: the route declares them and carries them.** `inputModalities` is `['text','image']` for every model the row does not mark text-only (`modalitiesOf`; the row's `vision`, true by default). The declaration decides the two refusals the user met: the session controller refuses a prompt carrying an attachment for a model that does not declare image input (reason `MODEL_DOES_NOT_SUPPORT_IMAGES` — the sentence "модель не поддерживает картинки" is that guard, and its input is this field), and the runtime replaces every picture of a message with the text-only placeholder before dispatch — which is why the pictures inside `read_image` results never reached the model while the model still spoke about them.
- The bytes come from the platform's own attachment store: the harness hands an adapter a durable reference and never bytes, and the route resolves it through `ctx.attachments.readImage` (`images.js`) into the vendor's own content part (`{"type":"image_url","image_url":{"url":"data:<mime>;base64,<data>"}}`). A user message and a tool result carry them; a picture the route cannot resolve, a block of any other kind, and a media type outside the vendor's four are **refused in words** with `UNSUPPORTED_CONTENT` rather than dropped, and an occurrence the platform marked `offloaded` stands as a placeholder. `imageRequestPricing` is declared and answers `undefined`: what a Qoder picture costs in tokens is not measured, and the platform's consumers fall back to their neutral estimate.

### The windows, and why these numbers

`contextWindow` travels nowhere: the chat body carries the model key, the reasoning flag and the output budget, and **no** context field at all. What the number buys is the platform's **condensing trigger**, `floor(min(W × 0.8, W − O − 65 536))` with `O` the routed output reservation (the same arithmetic in `resolveCompactSpec`) — the declared window is the budget of the conversation rather than the size of a request. So a window declared **too large** is spent as turns that come back as a summary instead of an answer, and one **too small** condenses a conversation the node would still have held: the cheap error is the first.

| model | declared window | where the number comes from, and what it buys at `O = 32 768` |
| --- | --- | --- |
| `dfmodel`, `qmodel_38max`, `qfmodel` (DeepSeek-Flash, Qwen3.8-Max, Qwen3.8-Flash) | **400 000** | the smallest tier of the vendor's own menu (`200 000 / 400 000 / 1 000 000`) above the depth this contour is read at — condensing at **301 696** |
| `auto` (Auto) | **400 000** | it publishes no menu, so no tier of the vendor's names this number; the declaration is the row's own — condensing at **301 696** |
| `efficient` (Efficient) | **200 000** | it publishes **no** menu; `200 000` is the catalogue's own model-level figure — condensing at **101 696** |
| a model the row does not declare | **200 000** | `DEFAULT_CONTEXT_WINDOW` (`adapter.js`) — the tier the catalogue marks as recommended — condensing at **101 696** |

The menu is chosen against this installation's provider journal (`$DSH_HOME/qoder-requests.ndjson*`), whose shape says the recommended tier is a recommendation to the client and not a ceiling on the node. Nothing on this route can select a **bigger** tier (no field of the body names one), so a window above 400 000 would buy no depth from the vendor and would only move the platform's condensing above every size this contour has been seen to answer.

What would move the number:

- **down**, to the largest prompt actually served, if a summary ever comes back for an ordinary turn well under 346 000 tokens — that would say the node holds less than it has been seen to hold;
- **up**, to the next tier of the vendor's menu (`1 000 000`), only on a measurement that the node answers normally with a prompt of that order: the trigger would then sit at 800 000, and no run of ours has pushed past 346 201 — the ceiling above it is **unmeasured**, and a probe that chased it would cost a long turn every time it missed.

A reservation larger than the window is a refusal rather than a risk: 256 000 reserved on `efficient`'s 200 000 makes `messageBudgetTokens` negative, `TargetPressureConfigError` is thrown, and that row falls back on the reactive recovery alone. The declared budget is also **not** a bound on the answer: `O` is the row's `maxTokens`, it enters the trigger, and the vendor does not treat it as a ceiling — the harness's own journal holds a request declaring `32768` answered with `42457` output tokens.

Neither the windows nor the trigger are ours to hold in code: the windows are the row's settings (`bundles/coreness.patch.yml`, with the same reason beside the numbers) and `O` is the row's `maxTokens`, so both are calibrated by a row edit.

### The credential door, and what the platform's page does with it

The row names a reference (`apiKeyEnv`), the store holds the value, and the route asks for it **per call**. Two findings from the live run are worth keeping:

- **`apiKeyEnv` must be declared `volatile`.** The settings service describes a namespace only when the schema declares a field whose writes apply without re-mounting the row (`volatileForm`), and the Models page keeps a provider row whose namespace it cannot read a profile from: the route can be registered and carried by the directory and **no row appear** until this field is volatile. A parsed volatile field is a live value, not a string — `referenceOf` reads through it, and `apply` takes the Loader's resolved config rather than re-parsing it.
- **The page draws a key field only for the two families it ships** (`layoutOf`: `llm-deepseek`, `llm-pi-ai`, anything else unknown), and for an unknown namespace it renders the hint that other fields live in `cordis.patch.yml` with Apply disabled. A route of our own is that third case by construction: the row, its **credential dot** and its identity are shown, and the key itself is entered through the store or the launching environment. The dot reports the truth either way — a configured reference reads `API key configured`.

**"Configured" means one thing: a value is there — never that the vendor takes it.** The store cannot answer the second question, and a token that expired, was revoked or belongs to a deleted account reads as configured until a turn fails; that has sent the owner to replace a token that was never at fault. The route's own `verify` action puts the value behind the row's reference to the **exchange every turn enters by** — one call, the value read through `readCredential` and never carried by a page — and answers in a closed vocabulary of three: `accepted`, `refused`, `unsettled`.

**What tells `refused` from `unsettled` is a code the vendor itself sent, never a status.** The contour answers `403` both for a value that is not active (`105`, `TOKEN_EXPIRE`) and for an account whose counted allowance is spent (`110`), and a status cannot tell those apart — our own `AUTH` says only that the envelope was 401 or 403. The body is read where it is still in hand (`in.js`, `refusalOf`), the vendor's code travels as a field (`QoderError.vendorCode`), and `verifyToken` convicts the value **only** by the three codes measured to be about it (`VALUE_REFUSED_CODES`: `105`, `TOKEN_EXPIRE`, `BadRequest`). **Everything else is `unsettled`**: a control call that did not answer, a transport fault, a `5xx`, a queue, a counted allowance, another code, an unparseable body, a moved door, a profile holding nothing. It is drawn as a question that could not be put and never as a refusal — "the vendor refused it" for a vendor merely unreachable would send a reader to replace a token nobody judged. The page asks when a value is handed over and when the reader presses again, and on an open it asks nothing: one exchange per write, one per press.

### The account's credits, and the widget's door

The widget shows the account's balance and the campaigns the contour offers; its figures travel over `CREDITS_ROUTE` (`/api/coreness.credits`) and never through this row's settings section, which is the profile's patch file.

**The three calls are not the chat wire.** They go to the OpenAPI host with a plain `Authorization: Bearer` of the **same job token** the chat turn uses and **without** the COSY signature — with the signature the contour refuses these addresses — and two of them introduce the client as the desktop one: without it the contour shows no campaigns, answering `showCampaign: false` and an empty list **without an error**, which is why "hidden" and "no campaigns" are two states here and in the widget. A repeat claim answers `200` with `replayed: true` or a body naming `ALREADY_CLAIMED` — an answer, not a failure.

`claimable` is computed **here**, from the contour's own status and action type (`CLAIMED`, `BLOCKED` and `EXPIRED` are out; an action type that is named and is not `CLAIM_BENEFIT` is out, while a record that names none stands as claimable, nothing recorded contradicting it), and travels to the widget finished: two owners of that flag — the half that parses the list and the half that draws the mark — would drift apart on the next field the vendor adds. A failure the contour names **inside a 200** is the same quiet outcome as a repeat; a refusal with a non-2xx status is a real refusal and stays visible as one.

The credits route's own answers are `{ok:true, value}` and `{ok:false, error:{code, message}}`. `last` is one of three states — `never`, `done`, `failed` with its code and words — and `sweep` names the cadence that produced it (`{everyMs, autoClaim}`), which is how the widget knows how often to ask again.

**The cadence, and why it is ten minutes.** The number lives in the row (`credits.sweepMs`), its reason beside it in `account.js` and here. The donor swept every five minutes and claimed automatically; its journal's median gap is 5.00 minutes, and what those five cost was a write into the profile's patch on every tick — **847 in four days**, with the donor's own session recording the consequence as a defect. This widget's figures travel over a route and write no file, so the cadence buys only a figure that is not stale and a reward that is not missed: the contour's reward window opens **once a day** and the balance moves with use, so **ten minutes** holds the figure as usefully as five at half the requests. The row may ask for another number; `MIN_SWEEP_MS` (1 min) and `MAX_SWEEP_MS` (24 h) bound it, and a row outside them is told so in the log and given the nearest honest value instead of being obeyed or refused.

**The automatic collection is on unless the row turns it off**, and its reason is the contour's own window: a reward that is not taken expires, and a claim that waits for a human press can lose a day of it. A repeat is an answer rather than an accident, so nothing is taken twice, and a failed claim is written into the picture's own `collection` rather than thrown away: silence about a reward that was not taken reads as a reward that did not exist.

**What is logged.** The mount says the route and the cadence; every sweep says what it read and how much is left; every claim says what was taken; a failure says its code and its words. The lines go to the platform's logger **and into the route's own answer** (`notes`, the last `NOTES_KEPT` lines): the answer is what a reader can see.

## The spend journal: what one request cost

`$DSH_HOME/qoder-requests.ndjson` is the donor provider's own ledger, and this route **continues** it rather than starting a second one: its rows stand as they are, and the boundary between the two eras is the `time` a row carries. The account's *balance* came back with the credits widget; what a single request cost did not.

**A row carries the spend alone** — the moment, the model, the ending, the duration, and the two counter objects the wire reported:

```json
{"time":…,"model":"dfmodel","finish":{"kind":"stop"},"durationMs":…,
 "usage":{"inputTokens":…,"outputTokens":…,"totalTokens":…},
 "vendor":{"credits":…,"originalCredits":…,"reasoningTokens":…,"cachedTokens":…,"billable":true}}
```

A row is one live turn: the vendor's own credits as they arrived, never a figure derived here, with the platform's counted tokens beside it. The donor's rows carried the whole request and the whole answer beside these counters, so `request`, `answer` and `process` are dropped here rather than written empty: the text of a conversation is not a journal's business. The two counter objects are written by the readers that already existed (`usageOf`, `vendorUsageOf`), whose keys are the donor's own, so one instrument reads both eras.

**When a row is written, and when none is.** At the end of an attempt whose answer carried a usage frame, **before** the terminal chunk leaves — a generator's code after a `yield` runs on the next `next()`, and a reader that stops at the terminal would leave the turn unrecorded. A turn whose answer carried no counters leaves no row: a row of zeros in a ledger of costs is worse than no row. A stream that broke *after* the counters arrived is still a charge the vendor made, so its row stands with its ending in it. A write never fails a turn: a path that cannot be written is said in the log with the path and the reason.

**The bound is this route's own number now: 64 MiB, on the user's word**, derived again from the rate this ledger's own life measures, and at that bound two generations are **128 MiB**. What the bound buys is a shelf life, because a row quoted **by line number** names nothing or another row after a rotation: a file at or above the bound is renamed to `.1` before the row is appended, and the generation the **donor** left moves once to `.1.donor` and stays — this README's own model-menu measurement quotes that journal, and destroying it would be a silent loss of a measurement — while every rotation after that replaces this route's own previous generation. The rotation lives in `spend.js` alone: `plugins/journal/rotation.js` was read first and does not fit, since it plans over records **with keys** and keeps a composition baseline, while this file is a plain append-only NDJSON.

**Where it is wired.** The route resolves the path once (`spendJournalPath`) and hands the journal to the adapter in `apply`, so a turn writes its row **wherever the route is mounted** — the harness's own sessions included. A tool that builds an adapter itself writes nothing unless it passes a journal: the live smoke does, and that run proves the module and the adapter's call point, while the wiring `apply` → `createAdapter({journal})` is held by the mount and the tests.

- `test/in.test.mjs` — the transport through a fake `fetch`: a pinned node, a cached token, one flight, a refresh falling back to the exchange, a fatal refusal, a missing credential making no call at all.
- `test/frames.test.mjs` — the channels, the three end-of-turn signals, the usage arithmetic (input excludes the cache), the tally; and a retelling counted with `textChars` at zero.
- `test/markup.test.mjs` — a test per treatment below, fed as the stream delivers it (the captured live call one character at a time); and the contract checks: a past reasoning block leaves **no tag at all** in the body, and a retelling leaves the answer's text empty while the counters name what arrived.
- `test/images.test.mjs` — the pictures of a request, and what is refused instead of dropped.
- `test/spend.test.mjs` — the row a canned stream produces, the row on disk **at the moment** a reader stops at the terminal, no usage frame leaving no row, a break after the counters keeping it, an unwritable path said in the log, and both generations at the bound.
- `test/probe.test.mjs`, `test/mount.test.mjs` — the discovery door in its three places (the registration where the mount does; what it answers where the contour does, the node's own listing with a model it does not enable left out; the mapping with the adapter, an unpublished window left out rather than filled with this row's fallback), and the route's own door: all three actions named in the refusal for a fourth, the listing verbatim, and a node that refuses answered with its own words and status.
- `test/probe.test.mjs` (the page's press) — one exchange and no more, the value read through the row's own reference, and the three answers told apart **by the vendor's own code**: `105` and `BadRequest` as `refused`, while `110`, another code, no body, a `503`, a queue, a moved `404`, a `200` with no job token and a profile holding nothing are `unsettled`.
- `test/adapter.test.mjs` (the other side of the listing) — a row naming a vendor level declares that level, and a row naming none keeps the route's own default: what the node advertises does **not** feed the declaration.

**A `200` is not a promise of content, and S9 is why that sentence is in this document.** Measured phase by phase, a corrupted signature is answered `200` with its headers at once, and then **a frame carrying the contour's own refusal** — a `data:` line whose body is `{"code":"101","message":"Signature invalid"}` with `statusCodeValue: 403` — at ~256 ms. The contour **names** the refusal; what misled every earlier run was the reader: the contour leaves that stream open (no `[DONE]`, no close), so code that waits for the end of the body waits ~180 s for a socket the vendor eventually closes, and a run that looks only at the status calls it a success. **A refusal inside the stream is now a refusal**: `chat` inspects the first chunk and any later frame, and the turn ends as `AUTH` in **1376 ms** end to end with the contour's own words. The ceilings below stay as the net for the case that really does say nothing.

## The ceilings — three numbers for three different things

Things can be waited on for too long in three different ways, and each has its own number — chosen, not inherited: two measured here and one from the harness.

| what is bounded | setting | number | why this number |
| --- | --- | --- | --- |
| **a control call** — the node map, the exchange, the refresh, the profile, the catalogue | `controlCeilingMs` | **10 s** | These answer in about a second, so this is tenfold headroom; the harness's plain-request default of 60 s is a default for a caller's *hint*, not a promise. On expiry the platform's retry policy (five attempts) is what heals it. |
| **the start of an answer** — the stream has opened and not one byte has arrived | `firstByteCeilingMs` | **60 s** | **This number is ours; the harness has nothing for it**, because for the platform's own providers a stream that never speaks is not a known case. The wait **grows with the prompt**, so 60 s holds for a cold prompt at least to the largest size measured, where the code's own default of 15 s — what a row that says nothing takes — holds only up to roughly half of it. It is a **time to first byte**, not an idle ceiling, and deliberately *not* the answer to a wrong signature: that case is refused by the contour in a fraction of a second, and a ceiling would only have hidden it. |
| **silence inside an answer that has started** — no byte for this long | `idleCeilingMs` | **300 s** | **The one number taken from the harness rather than measured here**: its own providers use `DEFAULT_STREAM_IDLE_TIMEOUT_MS = 3e5` for a stream read that outlives its demand. While a model produces a long reasoning stretch only the transport owes frames, and no measurement of ours says a legitimate gap is short — cutting this at seconds would risk killing a legitimate turn. |

**None of these is a ceiling on how long a turn may take.** An answer that keeps streaming is legitimate however long it runs; what is bounded is silence. The idle ceiling is armed **only while a read is outstanding** (the harness's own `idleWatchdog`), so the time the consumer spends thinking between lines is not counted as the vendor being idle.

The ceilings sit on the harness's own machinery, not on an arithmetic of ours: `clampTimeout` fills each unset number from its default and refuses a value that could not be a duration **before any work starts**; `deadline` arms the control and first-byte timers; `idleWatchdog` guards the read; `timeoutOf` tells a firing of ours apart from an upstream cancellation. The two endings are never confused: a ceiling that fires is **`TIMEOUT`** — the platform's word for a stalled request, one of the five codes its retry policy heals — while the caller's cancellation is **`ABORTED`**, an outcome of its own and not a failure. A stall must end as a request that did not answer, never as an agent that stopped; a wrong signing step is a third case again, and the best of the three — the contour names it, the vendor's own words and status travel in the message, and the code the platform routes on is this route's own reading, `AUTH`.

Every firing is counted, with the setting it belongs to, the value that fired, how long the wait had lasted and what was being done:

```json
{"ceiling": "firstByteCeilingMs", "ms": 15000, "elapsedMs": 15011,
 "where": "the Qoder chat turn (its headers)", "at": "2026-10-06T22:31:18.558Z"}
```

`transport.strikes()` returns what has fired so far, and the plugin also reports each one through the platform's logger, on the row that carries the settings, so "something is off" answers itself in numbers. A refusal is **not** counted here: the contour answered, and that is not a ceiling firing.

### These numbers are to be calibrated

All three are settings of the row — calibration is a row edit, never a code edit — and each states what observation would move it:

- **`controlCeilingMs`** moves **up** if control calls start answering near 10 s and read as a limit rather than as a failure; it moves **down** if the measurement stays at ~1 s across many days, since the headroom is then larger than the risk it covers.
- **`firstByteCeilingMs`** stands in the row at **60 000 ms** (`bundles/coreness.patch.yml`), while the code's own default of 15 000 ms stands for a row that says nothing. It moved up on the observation its own bullet named, and that condition is **met by observation**: at the judge's own size, **cold**, the vendor was silent about **thirty seconds** and then answered normally, `stop`. It moves **down** if ordinary turns are measured well under a second for a long stretch. What a probe costs, and why a ladder starts at the cheap end: **a call that is cut costs nothing** — no ledger row, a 0-byte feed — while a call that answers costs credits by its size, and **the account's quota is daily**.
- **`idleCeilingMs`** moves **only on evidence of a legitimate gap**: a single turn observed silent longer than 300 s that then delivered a correct answer. Absent that, it stays at the harness's number — the cost of being wrong here is a killed turn, and the cost of waiting is patience.

**What the two upper numbers stand on**: every session log of this machine, decompressed frame by frame by `node scripts/decode-session.mjs` and read for the `failure.code` of its `assistant/attempt` and `llm/retry` records, holds **no `TIMEOUT` at all** and not one failure sentence naming a ceiling — the only firings on record are the deliberate ones of the ceiling runs. **A ceiling of the far side's is not therefore a target**, and what has not been checked is whether the vendor ever legitimately keeps a turn silent longer than the **idle** number: one long **start** is on record, and that is the first-byte ceiling's business rather than this one's.

## Markup: the outgoing body carries no markup of ours, the way in gets a shutter

Two halves of one contract: **nothing of ours is written into the body that goes out, and nothing arriving in the visible channel is handled in silence.** A silent pass is not a simplification here — a hidden mishandling does not look like a failure, it looks like the model behaving strangely weeks later.

### Out: a past turn's reasoning travels in the message's own field

A recorded reasoning block belongs in the message's own `reasoning_content` field and not in the visible `content`, which carries the answer alone; the contour has a separate channel for it, the vendor's own client sets exactly that field on a past assistant turn, and `body.js` writes that shape — the answer alone in `content`, the thinking in `reasoning_content`, several thoughts of one turn set apart by a blank line because the field is one string. Nothing of ours is folded into the text the model reads as its own answer, which is the harm the shape removes: a wrapper invites the model to disown its own past words, and dropping the reasoning altogether made every run that tried it **invent** the missing fact. The order between a thought and the words it produced is not kept.

### In: one treatment per family, each one counted

The model sometimes writes its reasoning, a call or a whole retelling into the **visible** channel as tags. The shutter (`markup.js`) is fed every delta of that channel and decides what of it is text, what is reasoning, what is a call and what is nothing at all; the names of the families are `markup.js`'s own, and this list is the decision:

- **summary** — **dropped whole**: never answer text, never reasoning, never sent back up;
- **call** — **assembled** into a call when the block names a function; a block that names none, or that the turn ended inside, is routed to the reasoning channel instead;
- **reasoning**, **note**, **turn** and **echo** — **routed** to the reasoning channel;
- **unknown** — any other name is judged **by place**: in the wrapper position (nothing visible before it on its line) it is **routed** to the reasoning channel; in prose it is left in the text, because a tag-shaped word inside a sentence is a word of the answer;
- a **frame of an unknown kind** is **counted by name and carried**: the names not acted on come back in `unknownKeys`, the channel is decided by the keys the reader knows, and the turn goes on;
- a **frame that cannot be read at all** — not JSON, no usable status, a refusal envelope — is **refused in words**: the read fails with `FrameError` and the turn ends;
- a `finish_reason` spelled **`"null"`** is **read as no reason at all**: the turn settles by what it carried — an answer ends it by its content, no answer is an empty turn the policy re-asks. The vendor's own reader skips exactly that spelling, and the key **was** acted on, so it is not an `unknownKeys` name;
- the **sentinel** on a frame whose status is **not `200`** is **read as the end of the stream**: the body is the sentinel, and the status has nothing left to refuse. Narrow: every other body on a non-200 frame is still a refusal;
- a chunk-level **`error`** is **named and failed in words**: the attempt ends with the far side's own message, its own code and its status, as `SERVER` — the retryable code — and never as telemetry; their client takes this field **first** and fails the turn with it;
- a `data:` line that carries **no chunk** — the vendor's own timing frame — is **counted as telemetry**, not dropped in silence, and it is not refused: it arrives **once per turn in every feed saved here**. A line that is not `data:` at all is counted nowhere;
- **a tag split across deltas** is held: where a delta ends is the network's decision, not the wire's, so a fragment that could still grow into a tag waits for the rest of it and is released at the end of the turn.

Why each row reads the way it does:

- **The summary family is dropped, and this is the user's own decision**: the retelling is the model's own retelling of the dialogue, the harness is the one trusted to compact, and a retelling travelling back up would return to the model doubled. Dropped is not "dropped in silence": the pair is counted as two tag instances — the reading the donor's journal uses, `{"summary": 2}` — with the body's size and its head beside it, so *a retelling arrived, it was N characters, it said this* has an answer; the transport does not classify the **cause**, which is the listener's business and the adapter's step.
- **A call written as markup is a call.** Losing one is the donor's own defect: an answer wrapped in a container was swallowed and the turn closed as an empty response. The containers therefore include the outer call block of the striped form captured live, a parameter's value is taken as JSON when it is JSON, and a call is assembled only from a block the model closed itself: half a call is not a call.
- **The doubtful goes to reasoning, never to the answer.** The `assistant` and `tool_result` families follow that rule rather than the donor's more generous one, which kept a turn wrapper's body visible where the gateway sent no reasoning; the cost is named under "what is not covered" below.
- **An unknown name is judged by place**, the way the donor's instrument judged it: in the wrapper position it is the gateway's own wrapping, which this plugin has not learned yet; in prose it is a word of the answer — `A List<String> and a Bearer <token>` is text, and taking it away would be a loss nobody asked for. Both decisions are counted, so neither is invisible.

`tallyBody` (`frames.js`) reports the counters with every turn and `createShutter` keeps them per turn. The spend journal's row carries the wire's counters and not these, so what a turn met in the visible channel is said by the adapter's own line (`log` in `adapter.js`) whenever a turn produced any: a turn that lost a summary says so where the platform's own log is read.

### The one door where a summary body stays visible

The harness serves the auxiliary compaction call **through this route** (`ctx.llm.stream` with `purpose: "compaction"`), and its answer *is* a summary the harness asked for; dropping it would break the repair rather than protect the dialogue. So the shutter takes one option — `summary: 'keep'` — for that call alone, and the default for every ordinary turn stays **drop**: the option is the caller's to choose, not a heuristic of the reader's.

### What is not covered by these rules

- **A prose tag with a known family's name.** The name decides, not the position: an answer that mentions a call tag in passing loses the tag token to the reasoning channel (counted), and a run where a model writes a known tag inside prose is not among our measurements.
- **A summary block the model never closes.** The block is dropped and the rest of the turn with it; `markupUnclosed` says it happened.
- **A turn whose whole answer stands inside an `assistant` wrapper** ends without visible text, which the adapter classifies as an empty response and the platform re-asks; the donor would have shown that body as the answer. No row of either reading of the donor's journal shows the family firing, so the stricter rule costs nothing measured — and it cannot show a wrapper as an answer.
- **What a picture costs.** `imageRequestPricing` answers `undefined` and no request-image budget is declared, so both are left to the platform's neutral estimate: no measurement of Qoder's image accounting exists here, and an invented coefficient would be read as one. The platform's offload machinery exists for a route that enforces a budget, and this route enforces none, so **every picture of a session's history is sent on every turn of it**.

## Boundaries

- **The vendor's `max_input_tokens` is the fallback ceiling, not the window**: the fallback for a model whose catalogue carries no list, and the **denominator of the application's own accounting** (`context_usage_ratio = min(1, input_tokens / max_input_tokens)`). The window in force is the **ladder** the catalogue carries, so the `1M` the Qwen rows take stands as the catalogue gives it; this route sends no context field at all.
- **The route's own line ends at the adapter.** The wire owns the frames and the route owns the mapping, the classification and the declaration; anything of the harness's own loop — how a step is re-asked, how a tool error reaches the model — is read from the platform and not re-implemented here.
- **The live catalogue is not wired into `listModels`.** The models a picker offers are the row's, with the reason above; the vendor's catalogue remains a read of its own.
- **No donor code.** Nothing here is a copy of the donor's provider: the wire was read off the contour itself, and the implementation is written from that reading; no part of it carries a foreign licence, because no part of it is borrowed. The donor's code is cited where a decision rests on it — the families' spellings, the place that decides an unknown name, the size of the head kept.
- **The body carries no markup of ours, and none of our words either.** A past turn's reasoning travels in the message's own `reasoning_content` field (§Markup) and the visible `content` carries the answer alone; the check lives in the tests — no tag family, and no prose, is written into the body that leaves.
- **What is deliberately not built**: a settings page of the route's own — the route's settings live on the product's own page, where the section writes the model list and each row's reasoning effort through `settings.mutate`; the platform's own Models page cannot be their place, since a namespace the platform does not carry is drawn there as a stub — and the China contour with its own hosts and exchange. Pictures are built, and the credits are built with their boundary the other way round: the **value of a token** never travels here, and the balance is an observation held in memory rather than configuration of this row.
- **The token is never a value in this package.** Not in the config, not in the row, not in a log, not in an error message: only the reference's name travels. The one place a value is read is `readCredential`, and it is handed straight to the signature.
