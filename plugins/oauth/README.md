# @coreness/dsh/plugins/oauth — the flow, and only the flow

The OAuth flow a person takes to enter an MCP server that answers `401` with an authorization door: discovery, client registration, PKCE, the authorization exchange, the token exchange and refresh. The tokens it collects land in the platform's credential store and nowhere else, and nothing here connects a server, draws a row or touches the form — the flow is handed out as an address and taken back as a code.

## Dependencies

- **`credentials`** (`@deepseek-ai/dsh-credentials`), a hard dependency: every store of the flow is one of the platform's credential records. The seam is read live and its own contract is what this plugin is built on — `readRecord(key)` answers the record or `undefined`, `describeRecord(key)` answers `{configured, kind?, writable}` and never the value, `modifyRecord(key, mutate)` is the serialized read-modify-write whose mutate sees the value that stands while the write is exclusive and whose `undefined` **leaves the record untouched**, and `deleteRecord(key)` is the only removal, a no-op for a key that holds nothing. A record is `{kind, payload}`; this plugin writes `kind: 'grant'` and keeps its own JSON in the payload, which the seam returns as its owner wrote it.
- **The SDK's provider interface** (`@modelcontextprotocol/client`, 2.0.0, read at the installed assembly). The reading stands at that package's bundled provider interface and at the calls the client makes on it; the required calls, each with what it must answer, are: `redirectUrl` (a `URL` the browser step comes back to, whose absence selects the non-interactive flow), `clientMetadata` (what to register this client as), `clientInformation()` → the stored registration or `undefined`, `saveClientInformation(info)`, `tokens()` → the stored tokens or `undefined`, `saveTokens(tokens)`, `codeVerifier()` → the verifier string, `saveCodeVerifier(value)`, and `redirectToAuthorization(url)` for the hand-out of the browser step. The client looks for three more before calling them — `state()`, `saveState(state)` and `invalidateCredentials(scope)` with `client`, `tokens`, `verifier`, `state` or `all` — and this plugin answers those as well. The client's remaining optional hooks are left out on purpose: this client holds no secret to add to a request and makes no resource check of its own.
- **`node:crypto`** for the verifier and the state, and the standard itself for the addresses and the grammar.

## In the surface

The plugin publishes one name, `oauthFlow`, beside what it needs:

- `begin({server, resource, redirectUrl, pointer, clientId, scope, name, fetch})` → `{url, state, issuer, server, resource, clientId}`. It discovers, registers where the server allows it, keeps a verifier and a state, and answers the address a person opens. A registration the server already holds is used only while it names the address this sign-in comes back to: a provider holds the address of the request against the ones it registered, so a registration made at another port — a carrier restarted on a different one — is left behind and the flow registers anew, while a client id the caller named carries no address of its own and is taken as it stands. When the server registers none, the refusal names the address the standing registration holds instead of the one this sign-in cannot use.
- `finish({server, resource, code, state, redirectUrl, pointer, clientId, fetch})` → the tokens as stored. The state the answer carries is held against the state that was kept, and a code arriving with another state is refused. The state is taken back with the answer, before the exchange: a code is one-use, and a state that outlived its callback is a door left open for an answer nobody will send.
- `refresh({server, resource, pointer, clientId, scope, fetch})` → the tokens as stored, with the standing refresh token kept when the server re-issues none.
- `provider({server, redirectUrl, clientMetadata, handOut})` → the provider the SDK asks for, over the same stores.
- `stores(server)`, `idOf(server, part)`, `discover`, `resourceMetadata`, `serverMetadata`, `pointerOf`, `registerClient`, `authorizationUrlFor`, `exchangeCode`, `refreshTokens`, `pkce` (`verifier`, `challengeOf`, `isVerifier`), `words`, `codes` and `Refusal` — the pieces, so a caller needs no second import path.
- `forget(server)` → `{server, dropped}`. It removes everything this flow committed for **one** server — the four records its stores hold, each by the key this plugin derives from the folded name, and nothing else — and answers the keys that stood and went, in the order `tokens`, `client`, `verifier`, `state`. A server that holds nothing answers `{server, dropped: []}` rather than refusing: a row that never signed in has nothing to drop, and that is an answer and not a failure. What stood is asked with the seam's own description, so no token crosses the call, and the removal is the seam's own delete. A stored grant therefore goes with the row it belonged to, and a row added again is signed in again instead of silently remembering a token.
- `person`, `signIn({server, resource, pointer, clientId, scope, name, fetch})` and `redirectUrlFor(server)` are added to that same name while a platform web server and an authorization registry stand, and removed with the step: a surface outside this plugin starts a sign-in through the registry, and only the step's own wiring knows the carrier's port. `pointerOf` is published beside the discovery because a surface settling **whether** a row's server asks for OAuth reads the `401`'s pointer by the same rule the discovery reads it with, and a second spelling of that reading beside the page would drift from this one.

The stores stand under the credential scope `oauth`, one record per server per store: `oauth/<server>-tokens`, `oauth/<server>-client`, `oauth/<server>-verifier`, `oauth/<server>-state`. A server's name is a person's own word and may carry characters a credential id does not take, so it is folded to the id's grammar — lowercased, everything outside `a-z0-9-` folded to a hyphen, and a fold that would then lead with a digit takes `s-` in front, because the seam refuses a key segment that does not begin with a letter and it is the store's **parser** that refuses it: a key outside the grammar is written into the file and then takes the whole document with it at the next read. Two names that fold together share a record, which is why the folded name is a published call rather than a private one — and the pair the letter in front can put together is a name and the same name with `s-` before it. A name whose fold was already addressable keeps exactly the id it had, so no record under a key the seam could parse has moved; a name that leads with a digit derives different keys than it did before that letter, and a record an earlier sign-in committed for such a server stands under the unfolded key, which this plugin no longer names and no longer removes. The same function names the records a removal takes: `forget(server)` derives the four keys from the folded name instead of discovering them, because a scan of the scope takes every server of this plugin and a read by prefix takes a neighbour whose folded name begins the same way — `notes` and `notes-server` are two servers and one of them must not go with the other.

## The two habits of discovery, and which bed needs which

Both are tried, in this order, and a resource that answers neither is refused in words naming every address tried and why each answered nothing.

- **The pointer the `401` carries** — the `resource_metadata` parameter of its `WWW-Authenticate` header. Most measured beds name their document this way, and an address a server named itself is the first thing to ask.
- **The address the standard inserts before the resource's path** — `/.well-known/oauth-protected-resource` followed by the resource's own path. A measured bed publishes its document only there and names nothing in its `401`; a pointer that answers nothing falls back to this address rather than failing, which is what makes a stale pointer harmless.
- **The authorization server's metadata** is then read at the addresses derived from the issuer — `/.well-known/oauth-authorization-server` first, the OpenID configuration second, the path carried across. A measured bed publishes this metadata alone, with no resource document at all: the second habit is what finds it.

Dropping either habit loses a bed: the pointer alone loses the bed that names nothing, and the well-known address alone loses the bed whose document stands at the address its own `401` named and not at the derived one. The counts of the beds each habit serves stand with the reading that measured them, not here.

## The person's step, and the ground it stands on

The step is registered with the platform rather than drawn by this plugin: the person signs in from the platform's own surface, the platform's own web server takes the callback, and the flow's core finishes it. Every answer below was read live from the host's service contract, asked by name with the inspection providers rather than remembered; the one fact the live contract does not project — the carrier's listening port — was read in the installed carrier package's own code.

- **What a registration carries** — `{key, label, methods, run}`: `key` is the credential record the attempt obtains, `label` what a surface shows, `methods` a non-empty list of `{id, label}`, and `run(session)` the attempt itself. Registration returns its own disposer, and a second flow claiming one key is refused with `DUPLICATE_FLOW`, because two flows on one key would write one record in two formats.
- **How a person reaches a registered flow** — the registry lists entries as `{key, label, methods, inFlight}` and answers one key's entry with `describe(key)`; an attempt is started by `begin({key, method?, interaction, signal?})`, one attempt per key at a time, and a second caller is refused rather than joined.
- **What the session offers** — `{method, signal, commit(record), notify(notice), prompt(prompt)}`: `notify` carries `{message, url?, code?}`, `prompt` asks with `{kind: 'text' | 'secret' | 'select', message, placeholder?, signal?}` and answers with a string, and `commit` is the platform's own door for the record the attempt obtained.
- **What `begin` reports** — `{status}` with `authorized` or `cancelled`, where `authorized` means a record was committed **during that attempt** and observed; it throws `NO_FLOW`, `UNKNOWN_METHOD`, `ALREADY_IN_FLIGHT` or `NOT_COMMITTED` rather than reporting a quiet failure.
- **The callback's address** — `http://<loopback>:<the carrier's own listening port>/oauth/callback/<the folded server name>`, computed at the call and never written down: the port is the one the carrier is listening on, which is the port the operating system assigned when the configuration asked for none, and a carrier bound to all interfaces is answered on the loopback. A carrier that reports no listening port is refused in words rather than guessed at. The live service contract projects the carrier's methods and not this port, so the port was read in the installed carrier package (`@deepseek-ai/dsh-host-webserver`) itself: `port` answers the listening port, `host` the bind host, and the configuration takes `host` as one of the two literals with `port` up to 65535.

The step drives `begin` and `finish` from the core, hands the link to the session's `notify`, and waits for the code from whichever door answers first: the callback route, the person pasting what the browser showed them, which may be the code alone or the whole callback address, or the deadline that reads silence as an answer nobody will send. The tokens are written by the core and the record that stands is handed to the session's `commit`; what this plugin logs is a server's name and a refusal's code, and no code, token or secret reaches a log, a page, a file of ours or the process environment. A callback is refused with its own code where it cannot be finished, and an answer touches an attempt only by naming the state that attempt stored: the code that finishes it, the authorization server's own refusal that ends it, and the answer under the right state that carries no code all stand under that state, while a callback that names none, names another, or belongs to no attempt of that server is refused as it stands and leaves the attempt to its own answer. The state the attempt kept goes when the answer is taken and when the attempt ends without one, so nothing stands waiting for a callback that will not come.

**The answer a browser lands on is a page and not a protocol's line**: one sentence in the product's voice saying what the person must do — `Signed in — go back to the page and close this window.` — and, on a branch that could not be finished, the flow's own code in a dim line beneath it. What the authorization server said, and which link of the flow answered nothing, stand on the console's door with the step's own log line, where a reader who needs them looks; the page carries no address, no code of the flow's own body and no link, and the answer carries `cache-control: no-store` and `referrer-policy: no-referrer` because the address it stands at holds the code the server sent. The drawing is the product's own and invents nothing: the host's tokens are **named** where the platform defines them and never copied here — a second copy of a palette ages against the first — and the measures are the page's own roles, 14/22 for the sentence and 12/18 for the code in the face the page gives a code. A document served by this route stands outside the shell that carries those tokens, so where they do not stand the reader's own colour scheme draws the page rather than a colour of ours; where they do, they are what paints it. The four branches are four sentences and no branch is silent: the finished sign-in, an answer that could not be finished, an answer nothing waits for, and an address that is no callback of this plugin's at all.

**Every request the step makes carries a deadline**, and it is one number for the whole wire: `wireFetch(ms = WIRE_MS)` in `step.js` hands the platform's own `fetch` an `AbortSignal.timeout` unless the caller brought a signal of its own, so a server that accepts the connection and never answers ends the attempt with the discovery's own refusal — `no-resource-metadata`, naming the address that could not be reached, or `no-server-metadata` past it — instead of holding a person's sign-in open for ever.

**The browser step carries a deadline of its own**, and it is a person's measure and not a request's: `CALLBACK_MS` in `step.js` is ten minutes, after which the attempt ends with `no-callback`, naming the address the browser was told to come back to. The wire's deadline cannot answer this branch — a tab closed, a provider that never redirects and a callback that lands where nothing answers are indistinguishable from an answer still on its way — and without it the attempt waits for ever: measured on a live leg, a sign-in was still waiting fifty-eight minutes after it was handed out, with the state it kept standing and no tokens. The number is a decision and not a derivation: longer than any sign-in this product asks for, and short enough that a step nobody finished ends while the person is still in front of the page.

## Boundaries

- **The flow is all this plugin owns.** It does not connect a server, does not register tools, does not draw a row and does not know the form's fields: the platform's MCP client owns the connection and the page owns the picture. What it does own of the joint is the reference: `referenceFor(server)` answers the credential key a server's tokens stand under and the expression a row's header reads that token through, and the form that shapes rows writes both — the expression into the row's authorization header, and the row option `inject: [credentials]` beside it, in a write of its own before it, because the loader evaluates a configuration as the write lands and refuses an expression whose service is not yet in the row's context.
- **The expression stands where the row's own context stands.** It is evaluated by the loader synchronously, in the row's context, and it reaches the token through the store's record map — the installed local provider's own field, not an operation the credential seam declares, so this expression stands on that store and a provider put in its place would answer nothing. The core keeps a grant as a record of a kind and a payload, and this plugin writes the token response under `tokens`, so the token stands at `payload.tokens.access_token` — measured at the wire, with a payload of the other shape measured beside it and answering nothing. A record that is not there, a payload of another shape or a token that is not a string ends the row's activation with a sentence carrying `NO_TOKEN` rather than a header that means nothing.
- **No store of its own, and no secret outside the platform's store.** No file, no map, no process environment: a token this plugin holds is a credential record or it does not exist.
- **The browser step is a person's.** This plugin registers the flow, hands the link out through the platform's own session, and answers the callback; opening the browser, reading the page and deciding to sign in are the person's, and no check here pretends a session can sign in for anybody.
- **A refresh means the row is activated again.** The transport's options are fixed when it is built, so a rotated token reaches a connection only by that row being loaded again — and the door is measured rather than assumed: a write that changes nothing restarts the entry and leaves the header standing as it activated, while a fresh activation reads the store again and carries the new token to the wire. The price is named where the wrapper is described rather than hidden here.
- **The surface that offers the flow is the platform's**, and the joint is one the platform already defines: this plugin registers a flow per server with the registry and publishes `signIn` for whoever knows the servers; the page that shows a sign-in button and calls `begin` is a different card's work, and nothing of it stands here.
- **The callback's address is loopback.** The route answers on the carrier's own port and the redirect address names the loopback, so a server that accepts only a registered https redirect is a question this plugin cannot answer for itself: the flow that cannot be finished is refused in words rather than worked around.
- **The page a person lands on copies nothing of the platform's.** The host's tokens are named where the platform defines them — this tree declares none of them — and the document adds the page's own roles and no value of its own: no colour, no font stack, no address. A document served by this route stands outside the shell that carries the palette, so the drawing names what it cannot carry and lets the reader's own scheme paint it; a copy of the platform's values here would be a second palette, ageing against the first.
- **No organization of anybody's is named here.** No host, tenant, account or command line of anybody's stands in this plugin, its README or its checks; which servers a profile keeps is that profile's own file.
- **A client secret waits for a real registration.** The client is public and PKCE is what protects the exchange; fields for `client_id` and `client_secret` are not drawn until the first live registration says whether a loopback address is accepted at all.
